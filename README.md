# My To-Do — Flutter To-Do List (MVC + GetX + Firebase)

Lab task for **Mobile Application Development-II**. A To-Do List app with
Firebase email/password authentication and per-user task storage in
Cloud Firestore. It uses a strict **MVC** structure, with **GetX** handling
state management, navigation and dependency injection.

## Features

- Sign up, log in and log out (with a confirmation dialog). A splash screen restores the session.
- Forgot password (reset email), live "email already registered" check on
  Sign-Up, and a live password checklist (8+ chars, 1 letter, 1 number).
- Task reminders: a local notification at 9:00 AM the day before each pending
  task is due. Tapping it opens the task.
- Bottom navigation with three tabs: **Home**, **Calendar** (month view with
  task dots) and **Profile** (user info, stats, logout).
- Route guard: unauthenticated users can't open the main shell or the task screens.
- Real-time task list: add, edit, delete (with confirmation) and mark complete/pending.
- Total / Completed / Pending stat cards (tap one to filter the list).
- Search by title, filters (All / Pending / Completed), sorting (Priority / Due Date).
- Priority chips (High = red, Medium = orange, Low = green), overdue highlighting.
- Loading, empty, "no results" and error states.

Already done in this project: `flutter create`, adding the packages, and
`flutterfire configure` (which generated `lib/firebase_options.dart` and

### Commands you need to run

```bash
cd todo_app
flutter pub get        # download packages
flutter analyze        # should print "No issues found!"
flutter test           # model, validator and widget tests
flutter run            # run on a connected device / emulator
```

> Only re-run `flutterfire configure` if you switch to a **different** Firebase
> project. It needs `npm install -g firebase-tools`, `firebase login` and
> `dart pub global activate flutterfire_cli` first.

### Firebase Console steps (one-time)

1. Open <https://console.firebase.google.com> and select the project
   **todolist-7589d**.
2. **Authentication** → *Get started* → *Sign-in method* → enable
   **Email/Password** → Save.
3. **Firestore Database** → *Create database* → choose a location → start in
   **production mode**.
4. **Firestore Database → Rules**: paste the contents of `firestore.rules`
   from this project → **Publish**.
   (Or with the Firebase CLI: `firebase deploy --only firestore:rules`.
   `firebase.json` already points to `firestore.rules`.)

## 3. Viva notes

### MVC in this project

| Layer | Where | Responsibility |
|---|---|---|
| **Model** | `lib/data/models`, `lib/data/services` | Data classes (`UserModel`, `TaskModel` with `fromMap`/`toMap`/`fromFirestore`/`copyWith`) and the services that talk to Firebase. No UI code. |
| **View** | `modules/*/views`, `shared/widgets` | Only builds widgets. It reads state from the controller and forwards user events to controller methods (e.g. `onPressed: controller.login`). No business logic, validation or Firebase calls. |
| **Controller** | `modules/*/controllers` | All logic: validation, loading flags, search/filter/sort, calling services, navigation, snackbars and dialogs. |

Example flow for adding a task: `AddEditTaskView` → button calls
`TaskController.saveTask()` → validates the form → `TaskService.createTask()`
writes to Firestore → Firestore's real-time stream updates
`HomeController.allTasks` → `Obx` in `HomeView` rebuilds the list automatically.

**No duplicated widgets:** `TaskCard`, `CustomTextField`, `CustomButton`,
`PriorityChip`, `EmptyStateWidget` (also used for the error state),
`ConfirmationDialog` (used for both logout and delete), and so on are written
once in `shared/widgets` and reused by every screen. The Add and Edit screens
are the same widget (`AddEditTaskView`).

**No hard-coded values:** every string is in `AppStrings`, every color in
`AppColors`, every icon in `AppIcons`, every spacing/radius/size in
`AppSizes`, every text style in `AppTextStyles`, and the logo path in
`AppImages`.

### GetX state management (Rx variables + Obx)

- Adding `.obs` to a value makes it observable: `final RxBool isLoading = false.obs;`
  `RxList<TaskModel> allTasks`, `Rx<TaskFilter> filter`, `RxString searchQuery`.
- `Obx(() => ...)` rebuilds **only that widget** when an Rx value used inside it
  changes. Example: `Obx(() => CustomButton(isLoading: controller.isLoading.value, ...))`.
- Computed values such as `filteredTasks`, `totalCount`, `completedCount` and
  `pendingCount` are plain getters that read Rx values. Because they're read
  inside an `Obx`, the UI updates when any of those values change.
- `HomeController` listens to the Firestore `snapshots()` stream and calls
  `allTasks.assignAll(...)`, so every add/edit/delete shows up instantly.
- `TaskDetailsController` uses an `ever()` worker on `allTasks` to keep the
  details page in sync after an edit or toggle.
- Lifecycle: `onInit` (set up), `onReady` (after the first frame, e.g. the
  splash routing decision), `onClose` (dispose `TextEditingController`s and
  cancel the stream subscription).

### Named routes and middleware

- `Routes` (`app_routes.dart`) holds the constants `SPLASH, LOGIN, SIGNUP,
  FORGOT_PASSWORD, MAIN, ADD_TASK, EDIT_TASK, TASK_DETAILS`. `MAIN` is the
  bottom-navigation shell that contains the Home, Calendar and Profile tabs.
- `AppPages.routes` (`app_pages.dart`) maps each name to a `GetPage` with its
  page, **binding** and **middlewares**.
- Navigation:
  - `Get.toNamed(Routes.TASK_DETAILS, arguments: task)` pushes a page and passes data.
  - `Get.arguments` reads that data in the next controller.
  - `Get.offAllNamed(Routes.MAIN)` clears the back stack, so after login the
    Back button can't return to the login screen.
- `AuthMiddleware.redirect()` runs **before** a protected page opens
  (MAIN and all task routes). If `currentUser == null`, it returns
  `RouteSettings(name: Routes.LOGIN)` to redirect.
- `GuestMiddleware` does the opposite on LOGIN/SIGNUP/FORGOT_PASSWORD: a logged-in user goes to MAIN.
- The splash screen waits for `authStateChanges().first`, because Firebase
  restores a saved session asynchronously, and then routes to MAIN or LOGIN.

### Dependency injection: `Get.put` vs `Get.lazyPut`

| | `Get.put()` | `Get.lazyPut()` |
|---|---|---|
| When created | Immediately | The first time `Get.find()` is called |
| Used for | `AuthService`, `TaskService`, `NotificationService` (`permanent: true`) in `AppBinding` | Screen controllers: `MainShellController`, `HomeController`, `CalendarController`, `ProfileController`, `TaskController`, `TaskDetailsController` |
| Disposed | Never (permanent) | Automatically when its route is removed |

- `main()` runs `AppBinding().dependencies()` **before `runApp`**, so services
  exist before any screen opens, and `NotificationService.init()` can be
  awaited first (it must know whether a reminder tap launched the app).
- Each `GetPage` has its own binding that registers the controller for that
  screen. Views extend `GetView<XController>` and use `controller`.
- Services are **injected through constructors**, e.g.
  `HomeController(Get.find(), Get.find())`. This keeps controllers testable.
- `AuthController` is registered once with `Get.put(..., permanent: true)`,
  because auth state spans Login, Sign-Up and Home (logout). Tying it to one
  route would dispose its text controllers while another screen still uses them.
- `SplashController` uses `Get.put` in its binding because the splash view
  never reads it, and a lazy controller would never be created.

### Navigation: Home / Calendar / Profile

- After login the app opens **`Routes.MAIN`**, a shell screen
  (`MainShellView` + `MainShellController`) with a floating bottom
  navigation bar: **Home**, **Calendar**, **Profile**. `AuthMiddleware`
  protects it like any other page.
- `MainShellController.currentIndex` is an `RxInt`. Tapping a tab calls
  `changeTab(i)`, and an `Obx` swaps the visible page and the active nav item.
- The pages sit in an **`IndexedStack`**, so all three stay alive: switching
  tabs keeps scroll position, search text and filters.
- `MainShellBinding` `lazyPut`s all four controllers. **Calendar and Profile
  reuse `HomeController.allTasks`**, so Firestore is listened to only once.
  - **Calendar:** `CalendarController` builds the month grid (Monday first),
    marks days that have tasks with a dot, and lists the selected day's tasks
    with the same `TaskCard` (edit/delete/toggle go through `HomeController`).
  - **Profile:** name, email, the same three stat cards (`TaskStatsRow`) and
    Logout (the existing confirmation dialog). Tapping a stat card switches to
    Home with that filter.
- Android Back on Calendar/Profile returns to Home first (`PopScope` +
  `MainShellController.canPop`).

**Design system:** colors in `AppColors` (purple `#7C3AED`, lavender, mint,
peach), sizes in `AppSizes`, fonts in `AppTextStyles` (Plus Jakarta Sans for
headings, Inter for body, via `google_fonts`; the font files are bundled in
`assets/google_fonts`, so nothing is downloaded at runtime). The curved
header is one `CurvedHeader` widget (a `CustomClipper` wave plus a
`CustomPaint` leaf/sparkle), reused by every screen.

### How data is stored per user

```
users/{uid}                     ← UserModel: uid, name, email, createdAt  (NO password)
users/{uid}/tasks/{taskId}      ← TaskModel: userId, title, description, dueDate,
                                   priority, isCompleted, createdAt, updatedAt
```

- **Passwords** are handled only by **Firebase Authentication**, which hashes
  and stores them securely. They're never written to Firestore.
- `TaskService` always builds paths from the logged-in user's `uid`, so the
  app can only reach that user's own tasks.
- `firestore.rules` enforces this on the server too: `request.auth.uid` must
  equal `{userId}` in the path. Tasks are also validated: title 1–100 chars,
  priority is `low/medium/high`, `dueDate` is a timestamp, and `userId`
  matches the owner. Anything else is denied.
- Friendly error messages: `AuthService` maps `FirebaseAuthException` codes
  (e.g. `email-already-in-use`, `invalid-credential`, `weak-password`) to the
  readable messages in `AppStrings`.

### Authentication extras

**1. Forgot password**

- Login has a "Forgot password?" link → `Get.toNamed(Routes.FORGOT_PASSWORD)`.
  The route has its own `ForgotPasswordBinding`, which `lazyPut`s a
  `ForgotPasswordController` that is disposed when the page closes. The email
  typed on Login is passed as `arguments` and pre-filled.
- `AuthService.sendPasswordReset(email)` calls
  `FirebaseAuth.instance.sendPasswordResetEmail`.
- Firebase **email enumeration protection** is on, so Firebase never says
  whether an account exists. The app does the same: it always shows
  *"If an account exists for this email, a password reset link has been
  sent…"*, then a "Back to Login" button (`Get.back`). Real errors
  (invalid email, network, too many requests) are shown as snackbars.

**2. Email availability on Sign-Up**

- `fetchSignInMethodsForEmail` doesn't work with enumeration protection, so
  the app keeps its own lookup collection: `emails/{email}` → `{ uid, createdAt }`.
  The document ID is the trimmed, lowercased email.
- Sign-up writes `users/{uid}` and `emails/{email}` in **one batch** (both or
  neither). Login backfills `emails/{email}` for accounts created before this
  feature existed.
- `AuthService.isEmailAvailable(email)` is a single document `get` (from the
  server, never the offline cache) and returns `!exists`.
- In `AuthController` a listener copies the email field into an `RxString`.
  Two GetX **workers** watch it:
  - `ever(...)` → on every keystroke, status becomes `checking` (valid format)
    or `idle` (invalid), so an old result is never shown for new text.
  - `debounce(..., time: 600ms)` → only after typing pauses, one Firestore read.
    A late answer for an older email is ignored.
- `Rx<EmailStatus>` (`idle / checking / available / taken / error`) drives the
  field through `Obx`: spinner, green check + "Email is available", or red
  cross + "This email is already registered". The Sign-Up button is disabled
  while `checking` or `taken`. Firebase's `email-already-in-use` error is
  still handled as the final safety net.
- Trade-off: anyone can `get` one `emails/{email}` doc (needed before
  login), so an email's existence can be checked one at a time. The rules
  forbid `list`, so the collection can't be dumped.

**3. Password rules (Sign-Up only)**

- Rule: **at least 8 characters, 1 letter and 1 number.** No uppercase or
  special-character requirement.
- The rules live once in `app/utils/validators.dart` as the `PasswordRule`
  enum (label + `isMetBy`). `Validators.signupPassword` uses them, and so does
  the shared `PasswordRequirements` checklist widget, which sits in an `Obx`
  under the password field so each line turns green as you type.
- Login uses `Validators.loginPassword`, which only checks the password is not
  empty, so older accounts with shorter passwords can still log in.
- Unit tests: `test/validators_test.dart`. Widget tests for all three
  features: `test/auth_layout_test.dart`.

**Firestore rules for `emails/{email}`:** `get` is open to everyone, `list` is
denied, `create` only when logged in, the doc ID equals the token's email
lowercased, and `uid` equals `request.auth.uid`. `update` and `delete` are
denied from clients. Remember to **publish the updated `firestore.rules`**.

### Task reminders (local notifications)

**What happens:** every pending task gets one notification, *"Task due
tomorrow"*, at **9:00 AM local time the day before its due date**. The body
shows the task title and due date. Tapping it opens that task.

**How it works**

- These are **local scheduled notifications** (`flutter_local_notifications`).
  The phone's alarm system stores and fires them. No server or internet
  connection is needed, and they fire even if the app is closed.
- **Timezone:** `zonedSchedule` needs a `TZDateTime`. On start-up
  `NotificationService.init()` loads the timezone database (`timezone`) and
  sets `tz.local` to the phone's zone from `flutter_timezone`, so "9:00 AM"
  means 9:00 AM local time, including daylight saving changes.
- **Android setup:** core library desugaring (`desugar_jdk_libs`) in
  `android/app/build.gradle.kts`; `POST_NOTIFICATIONS` (Android 13+ asks the
  user) and `RECEIVE_BOOT_COMPLETED` permissions; and the plugin's
  `ScheduledNotificationReceiver` and `ScheduledNotificationBootReceiver`,
  which re-create reminders after a phone restart. The small icon
  `res/drawable/ic_notification.xml` is white-on-transparent, because Android
  draws status-bar icons from the alpha channel only (a colored icon shows as
  a white square).
- `AndroidScheduleMode.inexactAllowWhileIdle` is used. It can fire a few
  minutes late, but it doesn't need the `SCHEDULE_EXACT_ALARM` permission.
- Notification ID = a stable positive number computed from the Firestore task
  ID (FNV-1a hash), so the same task can always be found again to cancel or
  replace its reminder. The task ID is also the **payload**.

**Rules in `NotificationService.reminderTimeFor` (unit-tested)**

| Situation | Reminder |
|---|---|
| Task completed, or its due date has passed | none |
| 9:00 AM the day before is still in the future | at that time |
| That time has passed but the task is still upcoming (e.g. created the night before) | 1 minute from now |

**When reminders are scheduled / cancelled.** Controllers call the service
and the service does the work (MVC):

| Event | Where | Action |
|---|---|---|
| Task created | `TaskController.saveTask` | schedule |
| Title or due date edited | `TaskController.saveTask` | cancel old + schedule new |
| Marked completed / pending | `HomeController.toggleComplete` | cancel / schedule |
| Task deleted | `HomeController.deleteTask` | cancel |
| Login, or app start while logged in | `HomeController` (first Firestore snapshot) | `syncReminders(tasks)` |
| Logout | `AuthController.logout` | `cancelAll()` |

- `syncReminders` clears all *pending* reminders, then schedules one for every
  pending task. This also covers tasks created on another device. It skips
  the "1 minute from now" fallback; otherwise every app start would re-send
  a reminder for a task due tomorrow.
- Logout uses `cancelAll()` so the next person to log in on the phone never
  sees the previous user's reminders.
- Permission is requested **after login/sign-up**, not on app start.

**Tapping a reminder**

- App **running**: the plugin's tap callback → `NotificationService.onTaskTapped`
  stream → app-wide `NotificationController` → `Get.toNamed(Routes.TASK_DETAILS,
  arguments: taskId)`. If no one is logged in, it goes to Login.
- App **terminated**: `getNotificationAppLaunchDetails()` (in `init()`) records
  the task ID. `SplashController` routes to Home with it, and Home opens Task
  Details once ready.
- `TaskDetailsController` accepts a task ID, waits for the task list to load,
  and closes with "This task no longer exists" if it was deleted.
- Task Details shows a line such as **"Reminder: Thu, 15 Oct, 9:00 AM"**, or
  "No reminder" for completed/overdue tasks. The controller computes it.

**Demo:** log in (allow notifications when asked), then create a task with
tomorrow's due date. Because 9:00 AM today has usually already passed, the
"1 minute from now" rule applies, so the "Task due tomorrow" reminder arrives
about a minute later, even if you close the app. Tap it to open the task.
(If you demo before 9:00 AM, it arrives at 9:00 AM today instead.)
